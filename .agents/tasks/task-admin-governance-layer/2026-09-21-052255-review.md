# Human governance core: Directory, RBAC, kill switch, and admin audit (v1)

This slice adds the disaster-prevention backend from the Admin Panel Blueprint §5 MVP cut: a six-role RBAC matrix (`directory.py`), an org kill switch and append-only admin audit trail (`govern.py`), a membership seam on the identity layer (`identity.py`), key builders for the single-table model (`keys.py`), eight `/admin/*` routes wired to those pure functions (`api.py`), and the enforcement cut that fails a bot run closed when its org is frozen (`orchestrator.py`). The approach is faithful to the house rule that authz is code, not prompt: a lacked capability is `False`/absent, the acting subject is always re-derived from the verified token, and every state change writes a versioned, correlation-id-carrying audit row. RBAC, kill switch, and offboarding are all pull-based and fail-closed, and the last-Owner floor prevents an org from being left ungovernable.

Watch for: (1) **confirmed** — the invite/directory flow writes and reads member rows through `Store`, which stamps and filters every row on `ownerId == caller-sub`; because `org_id == user_id` today, an invited member's row is owned by the *inviter*, so the invitee can never read their own membership and the multi-user directory is non-functional end-to-end (single-tenant-only). This is a latent multi-tenant hazard baked into the data model, not just a follow-up gap. (2) **likely** — with `OWNER_SUBJECTS`/`OWNER_EMAILS` configured, `assert_owner` rejects every non-owner at `/admin/*` (and all other routes) before RBAC runs, so Admin/Security/Billing/Auditor seats cannot actually call the admin surface in a locked-down deployment. (3) **confirmed** — `_admin_list_members` returns raw member rows via `store.query`, exposing internal fields (`ownerId`, `gsi1pk/sk`) to the client.

**Verdict**: NEEDS_CHANGES

## High-level view

The RBAC matrix in `directory.CAPABILITIES` is transcribed cell-for-cell from the blueprint §4 table and is the single source of truth; a companion test re-transcribes it independently and checks every (role, capability) pair, so a silently-flipped cell fails the build. Enforcement is genuinely code-side: `can()` returns `False` for any non-ACTIVE member regardless of role, `assert_can()` raises the same `Escalation` the API already maps to 403, and there is no prompt in the path.

The kill switch and offboarding cuts are both fail-closed in the right direction. A missing kill-switch row reads as not-frozen (freezing is an explicit written act), and `orchestrator._drive` checks it at the pre-model chokepoint so a frozen org fails the next run before spending a token. Suspension is pull-based — `guard_principal` re-checks state on every admin request, so an in-flight actor dies on the next gated action rather than at a later sync.

The admin audit is append-only by construction: rows live under the org partition with an ordered `ADMINAUDIT#<iso>#<suffix>` sort key, carry a schema version `v` and an always-present correlation id, and are gated to an enumerated action set so a typo can't produce an unqueryable row. Offboarding is a state change to SUSPENDED, never a delete, so the trail survives the member it describes.

The single-table seam is modelled cleanly on paper — `ORG#<orgId>` partition, `MEMBER#<sub>` / `KILLSWITCH` / `ADMINAUDIT#` sort keys, no new GSI — but it collides with the `Store` tenant-isolation invariant. Every row carries `ownerId` and every read filters on it, and `owner_id` is the caller's own subject. Since `org_id == user_id` today, governance rows an owner writes about *other* subjects are owned by the owner, which is fine for the owner's own reads but means the seam does not actually generalize to multiple humans without reworking how `ownerId` is derived for org-scoped rows. The directory therefore works only in the degenerate one-human case, which the implicit-Owner default quietly papers over.

<summary>Issues (7)</summary>

1. **Member rows owned by the inviter** — `transact_put`/`put` stamp `ownerId = caller-sub` and all reads filter on it, so an invited member's row is invisible to that member's own `Store`; the invitee resolves to an implicit Owner of their own empty org and the multi-user directory never functions. Rework `ownerId` derivation for org-scoped rows (own the row by `orgId`, not caller subject) or document that this seam is single-tenant-only and gate the routes accordingly.
2. **assert_owner shadows the RBAC matrix** — with the owner allowlist configured, `_principal` → `assert_owner` rejects any non-owner subject at 401 before `assert_can` runs, so Admin/Security/Billing/Auditor seats can never reach `/admin/*`. Decide whether admin routes should bypass the owner allowlist and rely on RBAC, or document that only allowlisted owners may call them (which contradicts the point of the roles).
3. **Directory list leaks internal fields** — `_admin_list_members` returns raw rows (`ownerId`, `gsi1pk/sk`, timestamps) to the client. Project a member-facing view (subject, role, scope, state) instead of the stored row.
4. **Killswitch GET/audit read the caller's org, not a request org** — `_admin_killswitch_status` and `_admin_audit` query `K.org_pk(store.owner_id)` while the write path uses `actor.org_id`; identical today but two different notions of "the org" that will diverge the moment org_id ≠ user_id. Thread one org id consistently.
5. **Invite has no role/self/duplicate validation** — `_admin_invite` accepts any `role` string (raises a bare `ValueError`→500 on a bad value rather than 400), does not prevent inviting an existing subject (INVITED overwrites via create-only transact, which will 409 as a Conflict, not a clear error), and does not stop an owner inviting themselves. Validate role against `Role`, and return 400 with a clear message.
6. **Audit write is non-atomic for suspend/reactivate/role-change** — only invite uses `transact_put`; the other three do `store.update` then a separate `store.put(audit)`, so a crash between them leaves a state change with no audit row. Given "audit is what must never be lost," consider making the state change + audit atomic, or write the audit first.
7. **Blueprint MVP gaps for the next slice** — org ask-first policies + approval queue, usage/hard budget cap surfacing (`SEE_ALL_USAGE`/`MANAGE_PAYMENT` capabilities exist but no routes), impersonation break-glass (`IMPERSONATE` capability + audit actions exist, no route), and connector-revoke-by-admin are defined in the matrix/audit enum but unimplemented. Call these out as the deliberate follow-up surface.

### The RBAC matrix vs the blueprint §4 table

`directory.CAPABILITIES` maps each capability to a frozenset of roles with no inheritance and no wildcard, so an unlisted (role, capability) cell is a denied cell by construction — the mechanism that keeps "Auditor is read-only" true without a check anyone can forget.

The fidelity guard is the strongest part of the suite. `tests/test_directory.py` keeps an `EXPECTED` dict transcribed independently of the module and parametrizes over every (role, capability) pair, asserting both allowed and denied cells; widening a cell in `CAPABILITIES` without editing the test's independent copy fails the build. Values match the blueprint as described in the briefing.

`SEE_ALL_USAGE` and `MANAGE_PAYMENT` are correctly scoped to Billing/Auditor/Owner, but no route consumes them in this slice — worth naming so their correctness isn't mistaken for a shipped usage/budget feature.

### Enforcement is code-side and pull-based

The pull-based cut is tested at two layers: `test_a_suspended_admins_next_action_is_refused` seeds an ACTIVE Admin, confirms an invite succeeds, suspends that same subject in place, and confirms the very next invite returns 403 — failing in `guard_principal` before the capability matrix is consulted, which pins the ordering (state gate, then capability). `_membership()` re-derives the caller from the verified token on every request; `TestActorFromTokenNotPath` proves an attacker cannot suspend a victim by putting the victim's id in the path, and the audit row attributes the action to the token subject.

### The kill switch and the enforcement cut

The revert-proof test (`test_reverting_the_guard_would_let_the_run_proceed`) runs the same setup with the org *not* frozen and asserts the run completes, so the frozen-case failure is pinned to `assert_not_frozen` rather than an unrelated error. If the guard were deleted, the frozen test would reach the model path and its `org frozen` assertion would fail — the enforcement is genuinely load-bearing at the pre-model chokepoint in `orchestrator._drive`.

### Admin audit: append-only and correlation-joinable

Audit rows sit under the org partition with `ADMINAUDIT#<iso>#<ordered-suffix>` so same-second writes still sort distinctly, the read path is newest-first, the envelope carries `v` and an optional-in/always-out correlation id, and `ADMIN_AUDITED_ACTIONS` gates the action set so a typo raises rather than writing an unqueryable row. This satisfies the blueprint's "immutable admin audit distinct from per-run evidence, joined by one correlation id."

The append-only guarantee holds at the row-shape level (unique ordered sort keys, no update path), but the write *sequencing* is asymmetric across routes: invite is atomic via `transact_put([member_row, audit])`, while suspend, reactivate, and change-role do `store.update(...)` followed by a separate `store.put(audit)`. A failure between the two leaves a state change with no audit trail — the opposite of the stated invariant that the audit is the thing that must never be lost. Either make the state change and its audit row atomic, or write the audit row first so a partial failure over-records rather than under-records.

### The single-table seam and the ownerId/org_id hazard

The key layout needs no GSI change: `ORG#<orgId>` partition, `MEMBER#<sub>` / `KILLSWITCH` / `ADMINAUDIT#...` sort keys, plus a `gsi1pk = "ADMINAUDIT"` on audit rows for a future cross-org index, and a `(subject, role, scope, scope_id)` tuple that round-trips through `membership_of` for later workspace-scoped roles.

The hazard is the interaction with `Store`. Every write stamps `item["ownerId"] = self.owner_id`, and every read (`get`, `query`, `update`, `delete`) filters on `ownerId == self.owner_id`; `owner_id` is `principal.user_id`. Because `org_id == user_id`, an owner writing governance rows about *themselves* is consistent — the row's `ownerId` equals the org partition's owner. But an invite writes a `MEMBER#<invitee>` row under the inviter's `Store`, so the row is stamped `ownerId = inviter-sub`. When the invited human later authenticates, their `Store(invitee-sub)` reads `ORG#<invitee-sub>` filtered on `ownerId == invitee-sub` and finds nothing; `identity.load_membership` then hands them an implicit ACTIVE Owner of their own empty org. The invited seat is unreachable by the person it was created for.

The tests encode this rather than catch it: `seed_member(table, "bob", role, org=OWNER)` deliberately seeds under the owner's org, and `test_a_stored_membership_wins_over_the_implicit_owner` has to manually set `store.owner_id = p.org_id` for the lookup to resolve. `test_a_member_row_is_owner_isolated_on_the_shared_table` proves the row is invisible to a second store — correct tenant isolation, but it is exactly the mechanism that makes a real second human's membership unreadable. So the "seam" is sound as a *key layout* but the `ownerId` derivation makes it single-tenant-only in practice. Before this can carry real teams, org-scoped rows need to be owned by the `orgId` (and reads for governance need to key on org membership, not caller subject) — otherwise the multi-user directory is a data model that can be written but never read by anyone except the writer.

Compounding this at the API edge: `_principal` calls `identity.assert_owner`, which — when `OWNER_SUBJECTS`/`OWNER_EMAILS` is set — rejects any subject not on the allowlist with 401 before any route runs. An invited Admin or Security seat is by definition not an allowlisted owner, so in a locked-down deployment they cannot reach `/admin/*` (or anything else) at all, and RBAC never gets a chance to make its finer-grained decision. In an open (no-allowlist) single-tenant deployment this doesn't bite, but the two gates encode conflicting models of who may act.

### API surface and input handling

Eight routes: `GET/POST /admin/directory` (+ `/invites`, `/{subject}/suspend`, `/{subject}/reactivate`, `PATCH /{subject}`), `GET/POST /admin/killswitch`, `GET /admin/audit`. Literal paths register before the parameterized `/{subject}`, so `/invites` can't resolve as a subject. Capability mapping is defensible: list/audit gate on `READ_AUDIT_LOG` so a plain Member can't enumerate the directory, invite/reactivate/change-role on `INVITE_USERS`, suspend on `TERMINATE_COMPUTER` (a stretch, since the matrix has no dedicated offboard capability), killswitch on `CHANGE_ORG_POLICIES`.

Input handling has gaps that surface as 500s instead of 4xx. `_admin_list_members` returns `store.query(...)` rows verbatim, shipping `ownerId`, `gsi1pk/sk`, and timestamps to the client — project a view instead. `_admin_invite` builds `D.Role(body.get("role") or ...)`, so a malformed role raises a bare `ValueError` that falls through to the generic 500 handler, and nothing guards against inviting an already-seated subject (the create-only `transact_put` surfaces as an opaque 409 Conflict) or against self-invite. `_admin_change_role` reads `body["role"]` with a hard `KeyError` on a missing field (also a 500).

### Test coverage

Strong where it matters: the matrix fidelity guard, the pull-based cut at both the pure-function and HTTP layers, actor-from-token, the last-Owner floor (including a suspended Owner not counting toward the floor), the correlation-id round-trip, and the orchestrator freeze cut with an explicit revert-proof. The tests would fail if enforcement were reverted — the freeze guard, the RBAC gate, and the suspended-principal cut each have a test that flips to green only when the guard is present.

Not tested: the cross-owner invite path end-to-end (no test authenticates as the invited subject and checks they can read their own seat — which is precisely why the ownerId hazard went unnoticed); the `assert_owner`-vs-RBAC interaction under a configured allowlist; the non-atomic audit write failing mid-way; malformed-role and missing-field request bodies; and the leak of internal fields in the directory list response.
