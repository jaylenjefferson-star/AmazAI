# Admin governance follow-up: RBAC/allowlist split, honest single-tenant seam, view projections, audit-first writes (v2)

The fix commit (`1d22d43`) resolves the six in-scope issues from the v1 NEEDS_CHANGES review and defers the four blueprint MVP follow-ups (issue 7) as agreed. Token verification is now split from the coarse owner-allowlist gate so an invited Admin/Security/Billing/Auditor seat reaches `/admin/*` and is judged by the RBAC matrix, without weakening token verification or `Store` ownerId isolation. The multi-tenant `ownerId` hazard is made explicit rather than reworked: `load_membership` is scoped to the caller's own org and documented as single-tenant, with tests that authenticate *as* the invited human. Directory/audit responses are projected through view functions, all admin routes key on one `_admin_org_id(event)`, invite/change-role validate input to 4xx, and member/killswitch state changes now write the audit row before the state change so a crash over-records rather than losing the trail.

Watch for: (1) **confirmed** — the audit-first ordering for the *kill-switch freeze* means a crash between the audit write and the killswitch-row write leaves the org NOT frozen while an audit row claims it was frozen; for a freeze this is the operationally unsafe direction even though the trail is preserved (narrow crash-window, not a merge blocker). (2) **confirmed** — issue 1 is resolved only as "make it honest," so the directory remains genuinely single-tenant: a real second human cannot yet read their own seat. Acceptable for a disaster-prevention MVP given the documentation and boundary tests, but it must not be mistaken for a working multi-user directory.

**Verdict**: APPROVED

## High-level view

The v1 issue-2 conflict between the owner allowlist and the RBAC matrix is genuinely resolved. `_principal` now only verifies and caches the token; the new `_authorize` applies `assert_owner` for non-`/admin/*` routes and skips it for `/admin/*`, where each handler gates on a specific capability instead. All admin routes live under `/admin/directory`, `/admin/killswitch`, `/admin/audit`, every one caught by the `startswith("/admin/")` prefix, so no admin route escapes RBAC and no ordinary route accidentally bypasses the allowlist. The allowlist-vs-RBAC tests use the real `assert_owner` (only token derivation is stubbed), so they prove the reconciliation rather than mock it away.

Issue 1 is downgraded from "rework" to "make honest," which is the right call for a first mergeable slice. `load_membership` reads the MEMBER# row under the caller's *own* org and falls back to an implicit Owner of that same org — never a silent cross-tenant read. The limitation is spelled out in code comments and pinned by tests that authenticate as the invited subject and confirm they see their own empty org, not the inviter's roster. The seam is single-tenant by construction and honestly labelled as such.

The remaining fixes are clean: `_member_view`/`_audit_view` project only client-facing fields (tests assert the exact key set and the absence of `ownerId`/pk/sk/gsi keys); `_admin_org_id(event)` threads one org id through every admin read and write so status reflects exactly what set wrote; `_parse_role` and the invite guards turn bad/missing role, self-invite, missing subject, and duplicates into 400/409 instead of 500.

Audit-first ordering is the one place with a residual sharp edge. For suspend/reactivate/change-role, writing the audit before the state change is unambiguously the safe direction — a crash over-records. For the kill switch *freeze*, the same ordering means the audit can outlive a freeze that never landed, which for a kill switch is the direction you least want. The trail invariant is honoured either way, but the operational meaning differs and is worth a follow-up.

### The `_authorize` split (issue 2) — token verification intact, allowlist scoped

`_principal` no longer calls `assert_owner`; it only verifies and caches the token. `_authorize(event, path)` calls `_principal` then applies `assert_owner` only when `not (path == "/admin" or path.startswith("/admin/"))`, and `handler()` calls it in place of the old `_principal(event)` on the normalized (`rstrip("/")`) path. Every `/admin/*` route sits under `/admin/directory`, `/admin/killswitch`, or `/admin/audit`, all matching the prefix, so the allowlist is skipped for exactly the RBAC-governed surface and nowhere else.

The critical check: token verification is not weakened — `_principal` still runs the full `principal_from_event` (signature/iss/aud/exp) for every route including `/admin/*`, and only the coarse owner-allowlist decision moves to the per-capability gate. `Store(principal.user_id)` and its `ownerId == owner_id` stamping/filtering are untouched, so tenant isolation on the rows is intact. Each admin handler still calls `D.assert_can(_membership(...), <capability>)`, and `_membership` re-derives the caller from the verified token and runs the pull-based `guard_principal` state check.

The tests are load-bearing. `TestRbacSeatReachesAdminUnderAllowlist` sets a real `OWNER_SUBJECTS` that excludes the caller and only stubs `principal_from_event` (never `assert_owner`), then confirms: a non-owner Admin seat reaches `/admin/*` and can invite (201); a non-owner plain Member is refused by RBAC at 403 (so the allowlist bypass is not a free pass); and a non-owner on an ordinary route (`/agents`) is still rejected at 401 by the allowlist. Reverting the `_authorize` skip would flip the first case to 401 and fail the test.

### The honest single-tenant seam (issue 1)

`load_membership(store, principal)` reads `store.try_get(K.org_pk(principal.org_id), K.member_sk(principal.user_id))` and, on a miss, returns an implicit ACTIVE Owner whose `scope_id` is the caller's own `org_id`. Because `org_id == user_id == store.owner_id` today, an invited human authenticating with their own token reads their own (empty) org partition and resolves to Owner of that empty org — they never pick up the seat the inviter wrote under the inviter's org. The single-tenant reality is now enforced at the data boundary rather than papered over by a global implicit-Owner default; a genuine second human still cannot read their own seat.

`TestInvitedSeatIsSingleTenantHonest` and `test_identity.py::TestMembershipSeam::test_an_invitee_resolves_to_their_own_org_not_the_inviters` authenticate as the invited subject and assert they see an empty roster / resolve to Owner of `owner-b`, while the inviter's store still holds the ADMIN seat it wrote — these would have surfaced the v1 hazard had they existed then. Judgement: "make it honest + test the boundary" is an acceptable resolution for a first mergeable disaster-prevention slice, since nothing silently crosses tenants and the limitation is documented and referenced to `docs/architecture/03`. It is not a merge blocker, but the cross-org rework is a prerequisite for real multi-human teams.

### View projections (issue 3) and org-id threading (issue 4)

`_member_view` and `_audit_view` project a fixed field set; `_admin_list_members`, `_admin_invite`, `_apply_member_change`, and `_admin_audit` route every member/audit row through them. `TestDirectoryDoesNotLeakInternalFields` asserts the exact key set and the absence of `ownerId`/pk/sk/gsi1pk/gsi1sk/timestamps, so widening the stored row later cannot silently start shipping internals.

`_admin_org_id(event)` returns `_principal(event).org_id` and is now used by every admin read and write (list, roster via callers, killswitch status/set, audit) in place of the previous mix of `store.owner_id` (reads) and `actor.org_id` (writes). `TestOrgIdIsThreadedConsistently` freezes via POST and reads the same `reason` back via GET, pinning that status reflects what set wrote. Today the two notions coincide; threading one id removes the divergence the v1 review flagged for the day `org_id != user_id`.

### Input validation (issue 5)

`_parse_role` raises `A.ValidationError` (→400) on a missing or unknown role with an explicit allowed-role list, replacing the bare `ValueError`→500. `_admin_invite` now 400s on a missing subject and on self-invite (`subject == actor.user_id`) and returns a clear 409 (`already has a seat`) via an explicit `try_get` pre-check rather than the create-only transaction's opaque cancellation. `_admin_change_role` uses `_parse_role(body.get("role"))` so a missing field is a 400, not a `KeyError`→500. `TestInviteValidation` covers unknown role, self-invite, missing subject, duplicate (409), and change-role missing/unknown role, and asserts nothing is written on a bad invite.

### Audit-first ordering (issue 6) and its one sharp edge

`_apply_member_change` writes `store.put(audit)` before `store.update(...)` for suspend/reactivate/change-role, so a crash between them leaves an audit row without the state change — over-recording, the safe direction for an append-only trail. `TestAuditIsWrittenFirst` monkeypatches `Store.update` to raise, drives a suspend to a 500, and asserts the audit row is present while the member is still ACTIVE. This genuinely over-records and would fail if the order were swapped back.

The kill-switch path applies the same ordering (`store.put(audit)` then `store.put(row)`), and here the two safety notions diverge. For a *freeze*, a crash after the audit write leaves the org unfrozen (`is_frozen` reads absence/False as not-frozen) while an audit row asserts a freeze occurred — the trail leads the real state, and for a kill switch the un-applied freeze is the operationally dangerous outcome (an operator believes the org is stopped when it is not). The stated invariant ("the audit is what must never be lost") is still honoured, and the window is a single crash between two puts, so this is not a blocker; but "audit-first is always the safe direction" does not hold for the freeze action specifically. Writing the killswitch row first on freeze (fail-closed on the action) or deriving status defensively would close the gap.
