# Admin governance surface, kill switch, and two operator actions on AmazAI (review v1)

This slice re-integrates a superseded human-governance layer onto current `main` and extends it to the operator's asks: an RBAC-gated `/admin/*` API (directory, kill switch, append-only admin audit), a `reset-onboarding` and an `archive-memory` action, a deploy-time bootstrap that seats `admin@amazai.co` as an ACTIVE Owner without ever storing a password, and a separate `/admin` web console rendered outside the chat `<Shell>` with a typed-confirm + reason destructive-action UX. The core enforcement change is small and correct: `identity.assert_owner` moved out of `_principal` into a per-route `_authorize(event, path)` so `/admin/*` routes authorize through the capability matrix instead of the coarse owner allowlist, while every non-admin route keeps the allowlist exactly as before. The credential constraint holds — the forbidden literal appears nowhere in the tree or in git history, and the guard test is real (it assembles the literal from fragments and walks tracked source). Tests are behavioural: 298 tests across the new suites pass, and the RBAC-negative, suspended-admin, frozen-org, and append-only-preservation cases would each fail if the enforcement were reverted.

Watch for: the web Directory role picker offers `viewer` (not a real role) and omits `security`/`billing`/`auditor`, so a role change from the UI either 400s or cannot reach three of the six roles (confirmed); the typed reason in the confirm dialog is dropped for suspend/reactivate/reset/archive because those API wrappers take no reason argument, so the audit `detail` never carries the operator's justification the UX promises to record (confirmed); and the enforcement order in the two agent-lifecycle handlers is guard → assert_can → assert_not_frozen, not the guard → assert_not_frozen → assert_can order the design describes — harmless today since all three precede any write, but worth aligning (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The authorization cut is the load-bearing change and it is clean. `_principal` now only establishes identity from the verified token; `_authorize` applies `assert_owner` for every route except `/admin` and `/admin/*`, which defer to `directory.assert_can` on a specific capability. Non-admin routes are unchanged, so there is no privilege regression, and the token is still fully verified on admin routes — only the coarse allowlist is skipped in favor of the finer matrix.

Every admin handler re-derives the caller from the token via `_membership`, which runs `govern.guard_principal` (a suspended caller fails closed on their next action), then gates on a named capability before any state change or audit write. The kill switch is a single org-scoped row checked at the top of `orchestrator._drive`, so freezing stops the next run before a token is spent. The two write-ordering strategies (audit-first for member changes, state-first for freeze) are deliberate and documented to fail in the safe direction.

`reset-onboarding` is correctly restricted to the entrypoint Bot, resets only the systemPrompt and the starter thread's conversational messages, and never touches `AUDIT#`/evidence rows. `archive-memory` revokes (status → revoked, invisible next turn) rather than deleting, and leaves evidence and agent-audit rows byte-identical. Both are proven by tests that assert the surviving rows, not just the status code.

The single-tenant seam is honest: `org_id == user_id`, invites into a foreign org resolve to the invitee's own empty org rather than silently reading someone else's, and this is spelled out in `identity.load_membership` and enforced by the data boundary. The bootstrap seats the admin as Owner of its own org and documents that a cross-account admin is deferred.

The gaps are on the web surface and in the reason plumbing, plus one org-budget/kill-switch tie that is correctly recorded as a follow-up rather than built.

### The authorization cut: `_principal` splits from `_authorize`

The one change that could have caused a privilege regression is the relocation of `identity.assert_owner`. Previously `_principal` verified the token and immediately asserted owner; now `_principal` only establishes identity and caches it, and `_authorize(event, path)` decides whether the coarse allowlist applies:

```
_authorize(event, path)
   -> _principal(event)                     # token verify, always
   -> if path is not /admin and not /admin/*:
          identity.assert_owner(principal)   # allowlist, as before
```

Every non-`/admin` route passes through the same `assert_owner` it always did, so there is no privilege regression on the member surface. Admin routes skip the allowlist precisely so an invited non-owner Admin/Security/Billing/Auditor is not rejected at 401 before the matrix can decide — the token is still fully verified for them, and no admin route reaches a write without a subsequent `directory.assert_can` on a named capability. No admin handler reads a subject from the path or body: the `{subject}`/`{id}` is the target, the actor is re-derived from the token in `_membership`. The negative tests (`test_...member_cannot_...`, the plain-caller killswitch 403) confirm a non-capable principal is refused before any write.

### Fail-closed principal state and the pre-write gate

`_membership` runs `govern.guard_principal` on every admin request, so a caller suspended a moment ago holds nothing and their next action 403s rather than waiting for a sync — the pull-based offboarding cut. The suspended-admin tests mutate the caller's own `MEMBER#` row to SUSPENDED and prove the next reset/archive fails closed, which is the behavior that would regress if `guard_principal` were dropped.

The ordering caveat is real but non-blocking. The two agent-lifecycle handlers do:

```
D.assert_can(_membership(store, event), CAPABILITY)   # guard_principal + RBAC
govern.assert_not_frozen(...KILLSWITCH...)            # kill switch after RBAC
```

The design (and the member-write path) describe guard → assert_not_frozen → assert_can. Here `assert_can` precedes `assert_not_frozen`. Because both are pure checks that run before the agent is even looked up and before any write, the observable outcome is identical — a member on a frozen org still gets 403, an owner on a frozen org still gets blocked. The concern is only consistency and the "kill switch is the outermost gate" framing; reorder so a frozen org is rejected even for a principal who would also fail RBAC.

### reset-onboarding and archive-memory preserve the append-only trail

Both handlers were checked for the one thing that would violate the append-only guarantee: a hard delete of `AUDIT#`/evidence rows. Neither does. `reset-onboarding` clears only `MSG#` rows in the `dm-<id>` thread and resets `systemPrompt` via `A.plan_update`; `test_reset_leaves_append_only_agent_audit_rows_intact` asserts every pre-existing agent `AUDIT#` sk survives as a subset (the trail grows by the `agent.updated` row the prompt change appends — the invariant checked is old rows preserved, not an equal count, which is the honest way to assert it). `archive-memory` applies `memory.revoke()` (status → `revoked`, invisible next turn) rather than deleting; the test reads the row back and asserts it still exists and is no longer visible, and that the agent's `AUDIT#` rows are byte-identical before and after.

`archive-memory`'s `shared_rows` query is scoped to `K.user_pk(store.owner_id)` with `author == agent_id` — it archives only the current owner's partition and does not attempt a cross-owner read, so it is not a silently-broken cross-tenant read, just single-tenant-correct.

### Kill switch and the two write-ordering strategies

The freeze/audit write order is deliberately asymmetric: on FREEZE the state row is written first (a crash leaves the org actually frozen with at worst a missing audit row), on UNFREEZE the audit is written first (a crash leaves the org still frozen). Either partial failure lands in the more restrictive state. `test_a_failed_audit_write_still_left_the_org_frozen` monkeypatches the audit write to fail and proves the org is genuinely frozen afterward — an enforced fail-in-the-restrictive-direction, not a comment.

The member-write path (`_apply_member_change`) is audit-first for the opposite reason: a `MEMBER#` update cannot be transacted atomically with a create-only audit Put through the current Store API, so it over-records (an audit row whose state change did not land) rather than under-records. Consistent with "the audit is what must never be lost."

### Credential constraint holds and the guard is meaningful

`grep` across the tree and `git log --all -p` both return zero hits for the forbidden literal. `bootstrap_admin.py` reads and writes no password; it seats an ACTIVE Owner `MEMBER#` row plus a bootstrap admin-audit row, is idempotent, and documents that the password is set out-of-band in Auth0 with the identity keyed on `OWNER_EMAILS` until the sub is known. `test_no_password_literal.py` assembles the forbidden string from fragments via `"".join([...])` so neither the source nor its `.pyc` is a false offender, then walks tracked source asserting the literal appears nowhere — a genuine suite guard that fails the instant anyone hardcodes the credential, not a static assertion.

### Web admin surface: separate, gated, no composer, one real bug

`AdminShell` is rendered outside `<Shell>`, imports nothing from the chat surface, and offers only an "Open in member app →" link-out — the bot composer is genuinely absent. `AdminOnly` gates on `isOwner(user)` client-side over the server-side RBAC that is the real boundary, and `ConfirmAction` blocks until the typed token matches and a non-blank reason is entered (`ready = matches && hasReason && !busy`) before `onConfirm(reason)` fires. `demoApi` folds out of production (`grep -c demoApi dist/assets/*.js == 0`). Two confirmed issues sit on this surface.

The first is the role picker: `ROLES = ['owner', 'admin', 'member', 'viewer']`. The server's `Role` enum is `owner, admin, security, billing, member, auditor`. `viewer` is not a member of it, so `_parse_role` raises `ValidationError` → 400 (`unknown role 'viewer'`), and there is no way to assign `security`, `billing`, or `auditor` from the console at all. This is a UI-vs-contract mismatch that should be fixed by sourcing the role list from the real enum.

The second is the dropped reason. `ConfirmAction` collects a reason precisely because "every one of these actions lands in the append-only audit log and a reason is what makes that log worth keeping" (its own docstring), and `AdminDirectory.confirm` calls `pending.run(reason)`. But `run` for suspend/reactivate/reset/archive is `() => api.admin.suspend(m.subject)` — the reason argument is discarded, and those API wrappers send no body carrying it. So for four of the six directory actions the operator's justification never reaches the server, and the audit `detail` is a generated string (`suspended <subject>`) instead. `changeRole` (body) and the kill switch (`{frozen, reason}`) do forward their data, which makes the omission for the others an inconsistency, not an intended design. The reason should be threaded through these calls into the audit `detail`.

### Single-tenant honesty

The seam is documented and enforced, not hidden. `identity.load_membership` synthesizes an implicit ACTIVE Owner only for the sole owner of the store's own org; a human invited into a foreign org finds no row in their own org and resolves to Owner of their own empty org — they are not silently granted the inviter's org. `test_identity.py::TestMembershipSeam` authenticates as an invited subject to prove exactly this, so the single-tenant limitation fails safe rather than presenting as a working cross-tenant read. The bootstrap script and the task's deferred list both name the multi-tenant read path as the next slice.
