# Corrected admin role picker, reason-into-audit plumbing, and gate-order alignment (review v2)

This pass re-reviews the admin-governance slice after the author addressed the four confirmed v1 issues (the fifth, an org-wide budget cap, was a deliberate follow-up). The web role picker now sources the six real `directory.Role` values; a backend `_with_reason(base, body)` folds an operator's typed reason into the append-only admin-audit `detail` for suspend/reactivate/change-role/reset-onboarding/archive-memory; both agent-lifecycle handlers reorder to `_membership` (guard_principal) → `assert_not_frozen` → `assert_can`; and the reset/archive buttons are scoped to the Owner row. Three of the four fixes are clean and behaviourally tested. The fourth (button scoping) fixes the "buttons 400/404 on every row" symptom but the surviving Owner-row buttons still send the wrong identifier, so the two operator actions the user explicitly asked for cannot succeed from the console in production.

Watch for: the reset-onboarding and archive-memory buttons pass `m.subject` — the owner's user id — as the `{id}` path segment, but the server looks that up as an agent id via `K.agent_pk(...)`, and agent ids are derived from the Bot's name (`chief`), never the user subject; the call 404s in production and is only green in the demo because the stub ignores the id (confirmed). No enforcement regression: token verification, the owner-allowlist relocation, fail-closed principal state, append-only preservation, and the credential constraint all still hold after `dbe3cae` (confirmed). Full python suite is 1278 passed / 3 pre-existing `test_gaps_api.py` failures unchanged; web build strips `demoApi` (0 hits) and 145 web tests pass.

**Verdict**: NEEDS_CHANGES

## High-level view

The role-picker fix is exact: `AdminDirectory.jsx` `ROLES` is now `['owner','admin','security','billing','member','auditor']`, matching the `directory.Role` enum member-for-member, so all six roles are assignable and none 400s as an unknown role.

The reason plumbing is the strongest of the fixes. `_with_reason(base, body)` reads only `body["reason"]`, folds a non-blank trimmed value into the system-generated detail, and leaves the base string untouched when the reason is blank or missing. The subject/agent id is still read from the path, never the body, so the target of the action cannot be spoofed through the reason channel. It is threaded end to end: `api.js` wrappers send `{ reason }`, `AdminDirectory` `run(reason)` closures forward it, and `demo.js` mirrors the same fold so the demo trail reads identically.

The gate order is corrected in both `_admin_reset_onboarding` and `_admin_archive_memory`: `_membership` (which runs `guard_principal`) → `assert_not_frozen` → `assert_can`, with all three preceding the agent lookup and any revoke/audit write. The kill switch is now the outermost gate, so a frozen org is rejected even for a principal who would also fail RBAC. No admin path writes state or an audit row before its RBAC/kill-switch/principal checks.

The button-scoping fix is incomplete. Restricting reset/archive to `m.role === 'owner'` removes the buttons from member and suspended rows where they always 400/404, but the Owner row itself passes the owner's user subject where the server expects the entrypoint Bot's agent id. The console can display the actions but cannot complete them against a real backend — the same class of UI-vs-contract mismatch as the v1 role picker, now narrowed to one row instead of every row.

The org-wide budget cap remains a documented follow-up and is correctly not built; it is not re-flagged as blocking. The bootstrap for `admin@amazai.co` is unchanged and still seats an ACTIVE Owner with no stored password.

### Reset/archive still address the wrong identity (v1 #4, partially resolved)

The v1 concern was that the reset-onboarding and archive-memory buttons rendered on every member row, so clicking them on a non-owner or suspended row 400/404'd. `dbe3cae` scopes both buttons to the Owner row:

```jsx
{m.role === 'owner' && (
  <>
    <button ... onClick={() => setPending(resetOnboardingAction(m))}>Reset onboarding</button>
    <button ... onClick={() => setPending(archiveMemoryAction(m))}>Archive memory</button>
  </>
)}
```

That removes the rows that could never work. But the surviving Owner-row actions still key on `m.subject`:

```jsx
run: (reason) => api.admin.resetOnboarding(m.subject, reason),
run: (reason) => api.admin.archiveMemory(m.subject, reason),
```

`m.subject` is the owner's identity (the demo uses `'you'`; production uses the Auth0 sub / `admin@amazai.co`). The server treats the `{id}` segment as an agent id:

```python
agent = store.get(K.agent_pk(agent_id), "META")   # 404 if not this owner's
```

and agent ids come from `normalize_agent_id(profile["name"], ...)` — the Bot's slugged name (`chief`, `worker`), not the owner subject. The server tests confirm this: `seed_entrypoint_agent(..., agent_id="chief")` and every reset/archive test drives the endpoint with `chief`, while the web test asserts `resetOnboarding` is called with `'you'`. The two identifier spaces never coincide, so a real console click resolves `K.agent_pk("auth0|...owner-sub...")`, finds no META row, and returns 404. `store.get` raises `NotFound` on a miss, which the handler surfaces as a 404 — this is the exact fail mode v1 flagged, now confined to the one row that is still shown. The demo hides it because `demoApi.resetOnboarding`/`archiveMemory` ignore the id argument entirely and always return success, so the web test is green against a stub that does not exercise the identifier contract.

The comment added in `dbe3cae` asserts "the server resolves it to the owner's entrypoint Bot," but no such resolution exists in `_admin_reset_onboarding` or `_admin_archive_memory`; both use the argument directly as the agent id. The fix needs either a client-side lookup of the entrypoint Bot's real agent id (the console has no agent listing yet — the author notes this is the multi-tenant follow-up) or a server-side subject→entrypoint resolution, plus a test that sends the identifier the UI actually sends rather than the raw agent id.

### Reason folds into the audit detail without widening the trust boundary (v1 #2, resolved)

`_with_reason` pulls only the free-text reason from the body and folds it into the server-generated base string; the subject/agent id continues to come from the path, so the reason channel cannot be used to retarget the action:

```python
def _with_reason(base: str, body: dict) -> str:
    reason = (body or {}).get("reason")
    if isinstance(reason, str) and reason.strip():
        return f"{base} (reason: {reason.strip()})"
    return base
```

A blank or missing reason is a no-op, so the row is never worse than before — `test_a_blank_reason_leaves_the_base_detail_untouched` sends `{"reason": "  "}` and asserts `detail == "suspended bob"`, which would fail if the fold were unconditional. The five positive tests each seed a target, POST a distinct reason, and assert both the base phrase and the reason substring land in the detail of the correct action row; reverting any handler back to the bare `f"..."` detail would drop the reason substring and fail the matching test. The reason reaches the server through the full chain: `api.js` `suspend/reactivate/resetOnboarding/archiveMemory` now send `{ reason }` and `changeRole` carries it in its body; `AdminDirectory`'s `run(reason)` closures forward the value `ConfirmAction` collects; `demo.js` mirrors the fold via its own `withReason`. The `AdminDirectory.test.jsx` assertions were tightened to `toHaveBeenCalledWith('auth0|teammate', 'off-boarding')`, so a dropped reason argument fails the test.

### Gate order aligned; kill switch is the outermost gate (v1 #3, resolved)

Both agent-lifecycle handlers now run the checks in the documented order:

```python
membership = _membership(store, event)   # guard_principal: suspended caller fails closed
govern.assert_not_frozen(store.try_get(K.org_pk(_admin_org_id(event)), "KILLSWITCH"))
D.assert_can(membership, D.Capability.CHANGE_ORG_POLICIES)   # or TERMINATE_COMPUTER
```

All three precede the `store.get(K.agent_pk(...))` lookup and every revoke/audit write, so a frozen org is now rejected before RBAC even for a principal who would also fail the capability check. The suspended-caller and frozen-org negative tests still pass, which means the reorder did not open a path where a write or audit precedes the principal/kill-switch/RBAC checks. The member-write handlers (`_admin_suspend`/`_admin_reactivate`/`_admin_change_role`) do not call `assert_not_frozen` at all — they gate on `guard_principal` + `assert_can` only — so the "matching the member-write handlers" phrasing in the commit is loose, but that is a comment nicety, not a behavioural gap, and the freeze still stops bot runs at `orchestrator._drive`.

### No enforcement regression from dbe3cae (spot-check)

The v1-approved core still holds. `_authorize` continues to apply `identity.assert_owner` to every non-`/admin` route and skip only the coarse allowlist for `/admin`/`/admin/*`, with the token fully verified either way — the four handler signature changes in this commit only thread `body` into handlers that already received the verified event, and none reads a subject or actor from the body (`_actor`/`_membership`/`_admin_org_id` all derive from the verified principal). Adding `{ reason }` to the POST bodies does not create a new body-trusted field: `_with_reason` consumes only the free-text reason, and the target still comes from the path. Append-only preservation is unchanged — reset-onboarding still clears only `MSG#` rows and re-plans the systemPrompt, archive-memory still revokes rather than deletes, and neither touches `AUDIT#`/evidence. The credential constraint is intact: the forbidden literal appears nowhere in the tree, and `test_no_password_literal.py` remains a real guard.
