# Server-side entrypoint resolution closes the reset/archive identifier gap (review v3)

This final pass re-reviews the admin-governance slice after `58fd6e7` addressed the single blocking residual from v2: the reset-onboarding and archive-memory console buttons sent the owner's user subject where the server expected an agent id, so a real click 404'd and only the demo stub masked it. The fix splits each action into gate → resolve → shared worker, adds id-less `POST /admin/agents/entrypoint/{reset-onboarding,archive-memory}` routes that resolve the caller's own entrypoint Bot server-side (from the AGENTS index, never the body), reworks the console to load `GET /agents` so reset acts on the resolved entrypoint and archive carries each Bot's real agent id, and hardens the demo stub to validate the agent id so a regression fails a test instead of passing silently. The residual is genuinely resolved: a console click now drives the same identifier the server and tests use, and both the id-less and `{id}` paths reach a real agent.

## High-level view

The v2 residual is closed at the identifier level. reset-onboarding is inherently about the single entrypoint Bot, so the console sends no id and the server resolves `Chief` from the caller's own org exactly the way `GET /agents` does; archive-memory targets a specific Bot the operator picks from the roster, so it sends that Bot's real slugged agent id (`chief`, `worker`). The owner-subject-as-agent-id path is gone from both the client and the API.

The resolution never trusts the request. `_resolve_entrypoint_agent` queries the `gsi1` AGENTS index and takes the row with `entrypoint is True`, and `query_index` is scoped to `ownerId == store.owner_id` — the Store is bound to the caller's verified org (`org_id == user_id`), so the resolver cannot reach another org's entrypoint even if one existed. A missing entrypoint is a 404, not a silent no-op.

The gate order is preserved on the new handlers: `_membership` (guard_principal) → `assert_not_frozen` → `assert_can` run before the entrypoint lookup and before any prompt reset or memory revoke, matching the `{id}` handlers. The refactor into `_reset_onboarding_agent`/`_archive_memory_agent` shared workers moves no gate downstream of a write.

Route registration order is the load-bearing correctness detail: because `_match` turns `{id}` into a greedy single-segment capture, the literal `/admin/agents/entrypoint/...` routes are placed before the parameterized ones so `entrypoint` is dispatched to the resolver rather than looked up as `K.agent_pk("entrypoint")`.

The demo stub now validates the agent id against the roster and throws on a miss, and resolves the entrypoint the same way the server does, so the web tests exercise the real identifier contract instead of a stub that ignores the argument. The previously-resolved v1/v2 items (six-role picker, reason-into-audit, gate order, credential constraint, `assert_owner` relocation, single-tenant honesty) are untouched by `58fd6e7` and still hold.

### The v2 residual is resolved: console clicks now address a real agent

v2's single blocker was that `AdminDirectory` keyed both destructive actions on `m.subject` (the owner's Auth0 sub) while the server resolved the `{id}` segment through `K.agent_pk(...)`, and agent ids are the Bot's slugged name (`chief`), never the subject — so a real click 404'd and the demo passed only because the stub ignored the id.

`58fd6e7` removes the mismatch from both ends. The console now loads the roster alongside the directory (`Promise.all([api.admin.directory(), api.agents()])`) and derives the entrypoint from it. reset-onboarding sends no id at all:

```jsx
run: (reason) => api.admin.resetOnboarding(reason),      // -> POST /admin/agents/entrypoint/reset-onboarding
```

and archive-memory carries the picked Bot's real agent id:

```jsx
run: (reason) => api.admin.archiveMemory(agent.agentId, reason),   // agent.agentId is 'chief'/'worker'
```

On the server, the id-less reset route resolves the entrypoint and calls the shared worker on a genuine agent row, and the `{id}` archive route still looks up a real id from the path. The two identifier spaces no longer cross: `resetOnboarding` needs no id, and `archiveMemory` sends one that resolves. The demo mirrors this — `resetOnboarding(reason)` resolves the one `entrypoint: true` Bot, and `archiveMemory(agentId, reason)` validates `agentId` against the roster and throws `no such agent` on a miss, so a regression to sending a subject fails the stub rather than passing.

### Entrypoint resolution reads the caller's own org, never the body

Since the client no longer supplies the reset target, `_resolve_entrypoint_agent` is where a body-trusted-target regression could hide:

```python
def _resolve_entrypoint_agent(store: Store) -> dict:
    rows = store.query_index("gsi1", "gsi1pk", "AGENTS", limit=200)
    for row in rows:
        if row.get("entrypoint") is True:
            return store.get(K.agent_pk(row["agentId"]), "META")
    raise NotFound("this organization has no entrypoint Bot to reset")
```

The target comes entirely from the store, not the request body — the body carries only the free-text reason. `query_index` filters its results to `ownerId == self.owner_id`, and the Store is constructed against the caller's verified org, so the resolver can only see the caller's own entrypoint; there is no cross-org read even under single-tenant's `org_id == user_id`. It resolves through the same `gsi1`/`AGENTS`/`entrypoint is True` path that `GET /agents` and the console roster use, so what the operator sees on the Bots panel is what the server acts on. A NotFound surfaces as 404 rather than a silent success, and `test_reset_entrypoint_404s_when_the_org_has_no_entrypoint` seeds a non-entrypoint Bot and asserts the 404 with `entrypoint` in the detail.

### Gates run before resolution and any write on the new handlers

Both entrypoint handlers gate in the documented order ahead of the resolver:

```python
membership = _membership(store, event)                    # guard_principal: suspended caller fails closed
govern.assert_not_frozen(store.try_get(K.org_pk(_admin_org_id(event)), "KILLSWITCH"))
D.assert_can(membership, D.Capability.CHANGE_ORG_POLICIES) # or TERMINATE_COMPUTER for archive
agent = _resolve_entrypoint_agent(store)                   # only after all three pass
return _reset_onboarding_agent(store, agent, body, event)  # shared worker; write happens here
```

The kill switch is the outermost gate, so a frozen org is rejected before RBAC even for a principal who would also fail the capability check, and the resolver read and the prompt/memory write both sit downstream of all three checks. `test_entrypoint_reset_still_gates_on_rbac` seeds the caller as a plain MEMBER, drives the id-less route, and asserts a 403 with zero audit rows written — proving nothing is read or recorded before the gate. `_admin_org_id`, `_membership`, and `_actor` all derive from the verified principal, so threading the entrypoint route through them introduces no body-trusted subject. The refactor extracted `_reset_onboarding_agent`/`_archive_memory_agent` as shared workers whose docstrings state callers MUST gate first; both call sites (the `{id}` handler and the entrypoint handler) do, so no path reaches a worker ungated.

### `entrypoint` is not capturable as an agent id

`_match` compiles `{id}` to `([^/]+)`, a greedy single-segment capture, so `/admin/agents/entrypoint/reset-onboarding` would match `/admin/agents/{id}/reset-onboarding` with `id == "entrypoint"` if it reached that check. It never does: the literal `path == "/admin/agents/entrypoint/reset-onboarding"` and `.../archive-memory` branches are registered immediately before the two parameterized `_match` branches, so `entrypoint` dispatches to the resolver. If the order were reversed, the request would fall into the `{id}` handler and 404 on `K.agent_pk("entrypoint")`. `test_entrypoint_route_is_not_captured_as_an_agent_id` is the regression guard: it seeds a real `chief` entrypoint and asserts the id-less route returns 200, which would break if the literal route lost its precedence.

### The new tests are behavioural and driven by the UI's actual identifier

`TestEntrypointResolutionRoutes` drives the routes through the real `api.handler`/`_route` with the exact call the console makes — no agent id in the path for reset, and it asserts the server resolved to `chief` (`body["agentId"] == "chief"`) and that `is_brief(systemPrompt)` flips back to true, plus that the reason lands in the audit detail. The archive case seeds visible agent memory, calls the id-less route, and asserts the memory is no longer visible and `body["revoked"] == 1`. These would fail if the fix were reverted: without the id-less route the reset call would 404, and the assertions bind to the server-resolved id rather than a hardcoded path segment.

On the web side, `AdminDirectory.test.jsx` asserts `resetOnboarding` is called with only the reason (`toHaveBeenCalledWith('stale setup')` — a subject-as-id regression would add a positional argument and fail the exact-arguments match) and that archiving the second Bot fires `archiveMemory('worker', 'privacy request')` with the real agent id, not `'you'`. The confirm token for reset is now the fixed word `reset` rather than a user subject, and there is one Archive button per Bot keyed on the roster. The demo stub's roster validation means a future regression that reintroduces a subject as the archive id throws `no such agent` and fails the web test rather than silently succeeding.

### No new regression from 58fd6e7

The commit touches only the admin section of `api.py` (the two new routes, the resolver, and the extract-shared-worker refactor), the web console/api/demo, and tests. It does not touch `identity.py`, `orchestrator.py`, `govern.py`, `directory.py`, or the `_principal`/`_authorize` split — so the owner-allowlist behaviour on non-admin routes, the token verification, and the RBAC matrix are unchanged.
